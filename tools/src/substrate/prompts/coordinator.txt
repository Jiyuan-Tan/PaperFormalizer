CRITICAL, read twice: do NOT put file contents inside the JSON. Large Lean bodies inside a JSON string are the #1 cause of a parse failure that aborts the whole integration. Instead:

1. WRITE every file body and every insert patch as a SEPARATE FILE under the staging directory:

   Use short names, e.g. `{{STAGING_DIR}}/foo.lean`, `{{STAGING_DIR}}/merge_x.lean`. Put the EXACT bytes you want written/inserted into each staged file (namespaced, docstringed, ready to apply).
2. Emit ONLY a small JSON manifest that REFERENCES those staged files by `from` (relative to the staging dir). It contains no code — just short paths and one short anchor line per merge, so it always parses.

`{ "ops": [ … ], "notes": "<brief rationale: division, placement, reuse>" }`. `target` paths are RELATIVE to the toolkit root. Op kinds:

- `{ "kind": "create_file", "target": "{{LIB}}/<Division>/<Topic>/Foo.lean", "from": "foo.lean", "newModule": "{{LIB}}.<Division>.<Topic>.Foo" }` — write the staged `from` file as a NEW module at `target`; `newModule` must equal the module name of `target`.
- `{ "kind": "merge_lean", "target": "{{LIB}}/<Division>/<Topic>/X.lean", "anchor": "<a line already in X.lean>", "from": "merge_x.lean" }` — INSERT the staged `from` content after the first line containing `anchor` (empty anchor → append at end of file). INSERT-ONLY: the system preserves every existing byte and ROLLS BACK if a merge would change existing content. To add an import to an existing file, use a separate `merge_lean` anchored on the existing import line it sorts after (its `from` file holds just the import line). Multiple `merge_lean` ops may target the same file; combine dependent inserts that share one anchor into one staged file in dependency order. Pick a SHORT, UNIQUE anchor line.

## Hard rules
- NEVER modify or delete an existing line in an existing Lean file. Integrating is additive (new modules + insert-only merges). If it genuinely requires editing an existing proven declaration, pick a different placement and explain in `notes`.
- No `{{LIB}}.Staging` import or qualified reference may remain in a staged body.
- Every `target` is a `.lean` file under `{{LIB}}/<Division>/<Topic>/`; every `from` is a file you wrote under the staging dir. Do not edit barrels or `doc/ledger.json` — the system wires barrels and records provenance.
- Do NOT run the gate yourself — the system runs `lake build {{LIB}}` → module-header lint → toolkit layout lint → toolkit index, and rolls back on any failure. Emit only the manifest.
- `ops` is never empty. When the toolkit already provides every statement of the requirement, there is nothing to integrate: emit the one op that keeps what is new, or — nothing being new — an empty `ops` with `notes` naming the declaration that provides each statement; the run then stops with your notes for the orchestrator, and promotes nothing.
- Keep the manifest JSON small and valid: no code inside it, no trailing commas, all strings closed. If unsure, fewer ops with cleaner anchors.
